## 0. 结论

**信息不对称**：v0.3 是读过 B 之后写成的整合版（见其 §0.4、§17），还用上了用户在他们那边报告的实测结果：AAPL 三种模式下深度行数为 0，2152 消息列出 NASDAQ 和 IEX。B 写作时没有看到第三方的任何版本，也没有这条实测。所以 v0.3 在整合度上有先天优势。本文只比较两份文档本身，不比较作者能力。

**总体判断**：

- **v0.3 明显更好的方面**：数据语义的严谨性、证据与历史模型、验收方法、Agent 自主控制能力。
- **B 更好的方面**：交易员分析信号的广度、多标的盯盘、IBKR 消息码的运维细节、环境事实的核实深度、可读性。
- **最大分歧**：程序是否输出 consumed、pulled、absorption 这类归因标签。IBKR 的数据约束是：深度回调没有时间戳，逐笔成交时间只到秒，可见场所不全，没有订单 ID，报价按 250ms 快照更新。在这些约束下，v0.3 “只给联合证据、不打标签”的做法更站得住。B 的标签信息量更大，但在拿到可靠真值之前，误判的风险大于收益。
- **建议**：以 v0.3 作为 M0–M3 的实施基线，从 B 补入 6 项内容，并修正 v0.3 的 5 处问题（§6）。这一建议需要你决定。

**自查结论**：我在 B 中查出 12 个问题（§3.2），其中两项是实质性的：

1. B 的历史保存和 view 架构，支撑不了它自己承诺的“任意价位 300 秒归因”。
2. 成交与盘口减少量的匹配没有限定场所。

## 1. 评估方法

1. 通读两份文档全文，按 16 个维度逐项对比，每项都注明出处。
2. 复核 v0.3 的材料：
   - 用 Python 3.12.3 运行它的 12 项合成检查，结果全部通过。
   - 解析双方文档中的 JSON 代码块。v0.3 的 6 段全部通过；B 的 manifest 通过，B 的快照示例是带注释的 jsonc，按设计不参与解析。
   - 对 v0.3 的价带判定函数 `band_observation` 做边界输入测试（结果见 §4.2 第 3 条和附录）。
3. 事实核查：v0.3 新引用、而 B 没有覆盖的官方说法，逐条回到官方页面核对；同时重新核对 B 的关键说法（§5）。
4. 不评估的内容：
   - 实际运行效果。两边都还没有代码，也都没有盘中实测。
   - 各维度的重要性权重。§2 的计数只作为概览。

## 3. B 的优点与缺点

### 3.1 优点

1. **交易员视角完整**。
   - §3.1 写出了人类交易员读 L2 的六类做法；§3.2 给出工作流×角色矩阵；§3.3 列出 L2 能回答和不能回答的问题。
   - v0.3 以问题为中心，同样有价值，但没有系统描述交易员的读盘方法，它的 skill 里也缺这部分背景。
2. **支持多标的**。
   - 名额租约（§5.4.2）让 3 个深度名额可以同时服务 3 个标的，贴近开盘时盯多只股票的场景。
   - v0.3 首版只支持 1 个标的；换标的要 replace，旧的观察段会被切断。
3. **确定性微观结构特征更多**。
   - 包括 OFI（CKS 2014 原式）、update_rate、holes、regime，以及最优价在可见簿上的时间占比（§5.5）。
   - 这几项都是确定性计算，不涉及归因，可以直接被 v0.3 吸收。OFI 需要注明只基于可见簿的最优档。
4. **运维细节具体**。§2.2 为 14 个 IBKR 消息码逐一给出处理动作，其中包括 v0.3 没有单列的：101（行情线已满）、326（clientId 被占用）、354/10089/10186（权限类）、10197（竞争会话）。
5. **环境核实更深**。
   - 确认 Pi 0.87.1 是 npm 最新版（2026-09-22 发布）。
   - 直接阅读 npm 包内的官方文档和类型定义。
   - 下载官方 TWS API 归档，核对 SHA-256 与 pi-technical 的固定值一致。
   - 在 ibapi 10.50.2 源码中核对回调签名（size 为 Decimal 类型、DepthMktDataDescription 的字段）。
   - v0.3 自述没有核验归档，也没有确认最新版本（§0.4、§13.3）。
6. **具体，易于实施**。
   - 有完整的快照示例、工具参数清单、命令和 prompt 模板；篇幅约为 v0.3 的 71%。
   - M0 清单覆盖了 v0.3 核心 M0 不测的几项：TWS 深度窗口是否占用名额、numRows 上限、各交易时段、期货与债券深度、合规前置条件。

### 3.2 缺点（自查，按严重程度排序）

1. **【实质】历史保存与 view 架构撑不起自己的承诺**。
   - `levels` 分区承诺对任意价位给出“最近 60 秒和 300 秒的增减归因”（§5.8），但盘口增量只保留 120 秒（§5.4.5）。
   - view 沿用 L1 的做法冻结在 TS 端（§5.2、§5.7）。对一个新价位补算历史时，既不可能事先为所有价位预算好，TS 端也没有原始增量可用。
   - v0.3 把 ViewStore 放在 Python 端，冻结时 pin 住历史块（§4.1、§8.2–8.4），正好解决了这个问题。
2. **【实质】成交与盘口匹配不区分场所**。
   - 逐笔 `Last` 覆盖所有交易所的成交，而可见簿只有 NASDAQ 和 IEX。
   - B 的 flow_decomp、D2、D5 在 ±1.5 秒窗口内把成交和盘口减少量配对，但没有按 `exchange` 字段过滤，会把 NYSE 等场所的成交错配给 NASDAQ 盘口的减少（§5.4.4、§5.6）。
   - 再加上 v0.3 附录 B.6 指出的不可识别性（同一组观测可以对应多种成因），在拿到真值之前，这些类别标签并不可靠。
3. **主动方估计的基础薄弱**。B 用 L1 报价判断成交方向（§5.4.4）。但按官方说明，美股报价以 250ms 快照更新，逐笔成交时间只到秒；即使标注为 estimated，也难以避免模型过度信任。
4. **有过度表述**。
   - 摘要说用 NBBO 对照可以“量化可见订单簿的代表性”（§0 第 3 条）。价格一致不能说明数量覆盖了多少，v0.3 附录 B.5 的反例成立。
   - B 把 reqMktData 报价直接称作 NBBO，没有区分核实前和核实后的口径。
   - 我首轮回答说 `reqMktDepthExchanges` “只返回你当前权限下能拿深度的交易所”。官方原文只说“用户有相应订阅时，返回可以提供深度的交易所”，我的说法超出了原文。设计中把探测结果命名为 `quality.entitlements`，是同一个问题。
   - v0.3 把目录、通知、实际来源、实际请求分开存放（§3.2），这种做法更稳妥。
5. **用 minTick 构造价带和 tick 数**（§5.5）。官方说明 minTick 是“所有交易所、所有价位中可能出现的最小步长”，不一定是当前价位适用的步长。应改用 market rule，或者像 v0.3 那样首版只接受绝对价格区间。
6. **把未经核实的账户额度当成已知，自动降级会破坏可比性**。
   - 状态栏显示“L2 2/3”，收到 309 后自动下调名额（§5.4.2、§5.12）。这等于把没有核实过的账户额度当成已知值。
   - 负载过高时会自动减行、暂停低优先级订阅（§5.15）。这些操作虽然记为 D7，但改变了数据范围，前后数据不再可比。
7. **回放的成交没有隔离**。用 numberOfTicks 回放最多 1000 笔成交来缩短预热（§5.4.4），但没有规定把这些订阅之前的成交放进独立的历史段，它们会和订阅后的盘口时间线混在一起。
8. **D7 更正的范围过宽**。§5.6 规定“受影响时间窗内的 D1–D6 标记为 withdrawn 或 superseded”，但没有说明 317 这类正常重置算不算“受影响”，容易把此前有效的观察一并撤回。
9. **验收存在循环**。§6.3 的模型场景 (a)(b) 以 consumed/pulled 作为真值，而这些标签来自 B 自己未经验证的分类器。
10. **阈值多且未标定**。D1–D6 有 20 多个“初值”阈值。虽然标明了待标定，但一旦出现在事件输出里，就会显得像事实。
11. **措辞容易误读**。execution 分区的“同价位可见排队量”和“滑点”（§5.8），容易被读成“我前面还有多少排队量”和“预期滑点”。v0.3 用“同价已观察量”和“条件差额”，更准确。
12. **模型没有控制面**。watch、auto、record 只能由人类输入 slash 命令触发（§5.8）。模型只能通过 context 的隐式租约取数，无法自主建立持续观察或登记关键价位，这与“Agent 自主完成交易员工作流”的目标不完全吻合。

## 4. v0.3 的优点与缺点

### 4.1 优点

1. **可比较性判定严谨**（§6.2–6.3）。
   - 只有目标价带落在“已验证的返回前缀内部”时才给出带内总量：bid 侧要求 `worst < L ≤ U ≤ best`，ask 侧要求 `best ≤ L ≤ U < worst`。
   - 最差一档作为保护行，排除 SMART 深度尾部恰好截断在同价多行之间的情况。
   - 区分“前缀内观察为 0”“触及尾部”“越界未知”三种情况。
2. **时间有效性处理严谨**。
   - 持续时长、条件占比、覆盖比例都按有效时间积分计算，缺口不拼接（§6.5）。
   - 报价按字段记录接收时间，处理只更新 size 的情况（官方确有这种行为），以及锁定、交叉、单边报价（§3.3）。
   - B 用 1 秒采样，无法证明两次采样之间没有中断。
3. **证据模型完整**（§4.1、§8、§9.4）。
   - Python 是唯一的事实所有者；view 冻结时 pin 住历史块。
   - details 在冻结数据上做确定性补算，可以对任意价带重放实际保存下来的区间，并如实返回 available_from/to。
   - 按 seq 切分“当时已知的数据”，晚到的成交不会进入旧 view。
   - 分页使用 opaque cursor，不会漏掉同一秒内的多笔成交。
4. **Agent 可以自主控制**（§9.3）。
   - `depth_watch` 让模型自主启停观察、切换伴随输入、登记最多 8 个参考带、开关提醒和录制。
   - 参考带从登记时起持续积分，直接对应“盯关键价位”这一工作流。
5. **归因克制**（§7.3）。只给出联合证据，并注明成交场所与深度来源是否相容；不输出 consumed/pulled/absorption；用不可识别性论证这一取舍，论证成立。
6. **资源处理诚实**（§4.3、§10）。
   - 只报告本包自己的实际请求，账户上限未知就填 null。
   - 不自动减行，也不自动切换模式。
   - 三类溢出分开处理：入口溢出视为已知数据丢失，停止相应计算；历史淘汰只缩短回看范围；录制溢出只停止录制。
7. **自动提醒严谨**（§12）。
   - 只有一条规则，带滞回和 TTL，TTL 从首次满足条件起算、不续命；发送前再复核一次。
   - 参数必须显式给出，不提供看起来专业的默认阈值。
   - 另设一项评估，检验自动唤醒相对主动查询的价值。
8. **验收设计完整**（§15）。
   - 26 个命名用例。
   - A–F 分层输入对照，量化每类输入带来的增量。
   - 规定真值不能来自未经验证的分类器。
   - 上线前逐项写入 ACCEPTANCE.md。
9. **角色边界更合适**（§0.2、§1.2）。包本身不下单，但不禁止获得授权的宿主形成交易判断。这比 B 沿用 L1 的“不给交易指令”更适合交易员型或兼顾型 Agent。B 在待决问题 5 里提出了这个疑问，v0.3 给出了答案。
10. **过程透明**。§17 逐项说明从 A、B 吸收、修改和未采用的内容；对 12 项检查和 6 段 JSON，也如实说明只是合成验证。

### 4.2 缺点

1. **首版只支持 1 个标的、1 种模式**（§0.2、§10.1）。
   - 开盘时同时盯几只股票是交易员的常见做法，而账户默认有 3 个深度名额。
   - 换标的必须 replace，会切断旧的观察段，已完成的预热和积累的历史都作废。
2. **分析层整体推后**（§0.1、§7.5）。
   - OFI、事件候选、主动方判断都不进首版。首版以描述为主，识别工作交给模型，需要多次调用，也更耗 token。
   - 模型自己做的临时归因同样未经验证，而且可能更不一致。
   - 后续的“独立研究”没有给出真值来源和验证路线，“识别”这一交易员核心价值目前没有落点。
   - OFI 本身是确定性计算，把它推后的理由偏保守。
3. **判定函数有缺口**（本次复核发现，复现步骤见附录）。
   - **优于最优价的区域没有定义。** 文档（§6.3）和脚本都把“低于最优卖价的卖方价带”和“高于最优买价的买方价带”判为 out_of_range（未知）。但在返回集合里，这些区域必然没有挂单，应判为“前缀内为 0”。
   - **典型影响：** 卖方参考带 [100.02, 100.04] 被突破、最优卖价升到 100.05 之后，问“这段卖单还在吗”，正确答案是“可见簿上已经没有了”，按 v0.3 的判定却会返回“未知”。
   - **文档与脚本不一致：** 脚本把跨越最优价的价带（如 ask [100.01, 100.03]）标为 edge_truncated，而文档把 edge_truncated 定义为“触及最差返回价”。
4. **实施成本高，超出性能预算时缺少处理办法**。
   - M1–M3 要实现 checkpoint 加增量的历史重放、pin 块管理、用十进制字符串传输的 IPC、字段级报价时效、四种运行模式的验收和 26 个用例。
   - 单线程 reducer 在热路径上做 Decimal 运算和积分，高活跃标的有性能风险。
   - 文档设了测量门槛，但没有说明超出预算时怎么处理；同时它又不允许自动缩小数据范围。
5. **可读性较差**。
   - 约 4.2 万字符，禁止类措辞（不得、不能、不允许、禁止、不要）出现 99 次。
   - 没有一份完整的 depth_context 输出示例，需要实施者自己从表格推导 schema；§16.3 也承认完整 schema 待定。
6. **核心 M0 范围窄**（§14.2）。只测单一合约、单一模式、常规交易时段。TWS 深度窗口是否占用名额、rows 上限、盘前盘后时段，以及用户已经订阅的 ICE 期货和债券 L2，都不在核心 M0 里。
7. **合成检查的保障有限**。
   - 12 项中的 08–11 只是演示概念：比较两个相同的字典、测试 deepcopy、做列表过滤，并不检验算法。
   - 判定函数的测试没有覆盖上面第 3 条所说的区域。
   - test_12 只测了进入条件，没有覆盖退出、滞回和重入。
   - v0.3 自己如实说明了这些检查的范围。
8. **manifest 的小问题**。
   - 同时写了 `"private": true` 和 `"keywords": ["pi-package"]`，而这个关键字只在公开发布时有用。
   - `files` 写的是整个 `python/market_depth/` 目录，可能把 `__pycache__` 打进发行包。L1 用 `**/*.py` 避免了这一点；v0.3 §13.4 规定的打包检查能发现这个问题。
9. **有未做的核实**：没有核验官方归档摘要，没有确认 0.87.1 是不是最新版。这两点它都已自述。

## 6. 建议的整合路线

### 6.1 基线

以 v0.3 的 §0–§16 作为 M0–M3 的实施合同。

### 6.2 从 B 补入

1. IBKR 消息码处理表（B §2.2），补上 101、326、354/10089/10186、10197 这几项的处理动作。
2. 在 M2 加入几项确定性特征，只计算，不下结论：
   - 可见簿最优档的 OFI（按 CKS 2014 原式，注明只基于可见簿）；
   - update_rate；
   - 前缀内的空档；
   - spread 和深度相对本次观察基线的比值。
3. 把交易员读盘方法（B §3.1–3.3）写进 skill 的 references，作为模型提出假设、寻找反证时用的检查清单。B 的几类事件（挂单墙被吃或被撤、吸收、扫单、流动性变薄）只作为待检验的假设，不作为程序输出的标签。
4. 把多标的支持（B 的名额租约）列为 M4 的候选。如果纳入，要遵守 v0.3 的规则：只报告本包自己的占用，不猜测账户额度，不自动回收用户显式建立的观察。
5. M0 追加三项低成本测试：
   - TWS 深度窗口是否占用名额；
   - numRows 的实际上限；
   - 合规前置条件（API Acknowledgement、10197 竞争会话）。
6. 写入已核实的环境事实：Pi 0.87.1 是 npm 最新版；官方归档摘要与固定值一致；B 的固定版本是提交 `2d819bc`。v0.3 附录 A.1 提到 B 的分支引用可能变动，这个提交号可以直接作为固定引用。

### 6.3 v0.3 需要修正的地方

1. **判定函数**：补上“优于最优价 → 前缀内为 0”，让脚本的 edge_truncated 与文档定义一致，并补充相应测试。
