## 0. 摘要

### 0.1 定位

pi-orderbook 让 Agent 像顶级交易员一样使用 L2 数据：

- **程序**持续观察订单簿和成交流，按交易员关心的方式度量变化，在值得关注的时候唤醒模型。
- **模型**负责推理：解读证据，提出并检验假设，制定和修订观察计划。
- **宿主**决定 Agent 的角色：只盯盘、边盯边做，还是只做执行。

L1（完成柱、指标、结构）由 pi-technical 负责。本包只做 L2，也就是订单簿，外加理解订单簿变化所必需的成交流和报价参照。

### 0.2 对四点需求的回应

| 需求 | v2 的设计 | 章节 |
|---|---|---|
| 1. 不写死标的数 | 不设标的上限，容量以 IBKR 实际接受为准；深度名额随行情线数和 Quote Booster 增加[官方]，账户升级后不用改代码。名额分固定、任务、升舱、临时四级管理，只自动回收后两级。“按需升舱”让观察清单平时只占 L1 行情线，价格接近关键价位时才申请深度 | §4 |
| 2. 周末只做设计 | 依赖实盘的事实都设计成“按模式核验后启用”，不阻塞设计和离线开发；核对项集中在附录 B | 附录 B |
| 3. 金融理解、程序唤醒、主动调用 | 唤醒是核心能力。模型用受限的条件语言登记 if-then 观察计划并附论点备注，程序持续判定，再按紧急程度选择 Pi 的投递方式：紧急的用 steer 插入当前运行；普通的等 agent 空闲后新开一轮，发送前复核新鲜度；背景信息用 nextTurn 随下一条用户消息附带。十类可观测模式和注意力预算负责过滤噪声。主动调用的输出以“相对自身基线的变化”和“双向证据”为中心。金融知识写进 skill：读盘流程、模式假设手册、市场结构知识 | §7–§9、§11 |
| 4. 角色不写死 | 能力与角色无关，角色只改变默认值。提供 monitor、hybrid、execution 三种 profile，可按标的覆盖，也可运行时切换。执行场景通过“订单上下文”获得排队、止损区流动性、静态冲击分析和紧急唤醒。本包不下单：下单由宿主或专门的执行包负责，本包通过 `pi.events` 给执行包提供确定性信号 | §10 |

### 0.3 核心设计决定

1. **按时间尺度分工**：程序负责毫秒到秒级的观察、度量和过滤；模型负责秒到分钟级的推理和计划；需要毫秒级反应的动作写成预授权规则，放在本包之外。
2. **证据分四级**：观测、推导、推断、解读。只有前两级可以直接触发唤醒。
3. **不输出原因标签**：不输出“被吃掉”“被撤走”“吸收”这类结论，只输出可观测的联合证据，例如下降量中有多少被同场所成交覆盖。原因交给模型推理。
4. **可比较性优先**：价格带完全落在已返回的视图内时才给总量；区分“视图内为零”“尾部不完整”“视图外未知”三种情况，并修正了 v0.3 判定中的缺口。
5. **Python 是唯一事实所有者**：冻结 view 时连同历史一起冻结；“当时可知”按全局序号切分。
6. **观察计划是 Pi 分支状态**：watch、价格带、订单上下文跟随会话分支，会话恢复后可以还原。
7. **容量由券商决定**：不猜账户总额。来源、档位、成交流层级的任何变化都在输出里披露，不静默降级。

## 1. 设计原则

### 1.1 按时间尺度分工

| 层 | 时间尺度 | 负责 | 位置 |
|---|---|---|---|
| 观察与度量 | 毫秒–秒 | 维护订单簿和成交流、计算特征、判定条件、过滤噪声 | 本包 Python worker |
| 推理与计划 | 秒–分钟 | 解读证据、提出并检验假设、登记和修订观察计划、在授权范围内形成判断 | 模型（Pi Agent） |
| 预授权反应 | 毫秒–秒 | 例如“止损区买盘消失就撤单”这类确定性规则 | 执行包或人，在本包之外；可以订阅本包的信号 |

模型推理一轮通常要几秒到几十秒，订单簿却以毫秒为单位变化。交易员之所以提前做 if-then 计划，正是因为盘中来不及临场思考。所以本包让模型把计划登记成 watch（§8.2），由程序实时判定，条件成立时叫醒模型。模型的价值在于制定和修订计划，以及在关键时刻做判断。

### 1.2 证据分四级

| 级别 | 例子 | 能否直接触发唤醒 | 必须附带 |
|---|---|---|---|
| 观测 | 行、成交、报价、IBKR 消息 | 能 | 来源、本地接收时间、epoch |
| 推导 | 价差、带内量、失衡、OFI、成交覆盖率、存续时长、模式 P1–P10 | 能 | 定义、窗口、可比较性状态 |
| 推断 | 主动方估计、BVC 净量 | 默认不能；需显式开启并标注 | 方法、假设、可靠性统计 |
| 解读 | 模型提出的假设和判断 | — | 在模型输出中引用证据 |

### 1.3 其他原则

- **未知不是零**：超出视图、单位未核实或预热不足时，输出 null 并写明原因，不输出 0。
- **证据冻结，当时可知**：模型用 view_id 补读时，拿到的是同一时刻的全部证据，包括历史。之后才收到的数据不会混进旧 view。
- **注意力由意图驱动**：优先唤醒与模型自己的计划、价位、订单有关的变化，其次才是显著的市场变化。
- **容量由券商决定**：不写死数量，也不猜账户总额；优先级和回收规则都是显式的。
- **能力与角色无关**：所有能力在任何角色下都可用，角色只改变默认值。
- **Pi 原生**：遵循 Pi 的生命周期、分支状态和消息投递语义；不另建一套 agent 框架，也不在包内另行调用模型。

## 2. L2 的价值：顶级交易员怎样用它

### 2.1 三类数据

| | L1 顶层报价 | L2 深度 | 成交流（Time & Sales） |
|---|---|---|---|
| 回答的问题 | 最优价在哪里 | 各价位挂了多少，挂在哪个场所或由谁挂出，怎么变化 | 实际成交了什么，在哪里成交，成交有多快 |
| IBKR 接口 | `reqMktData`，美股按 250ms 快照更新[官方] | `reqMktDepth`，不采样不过滤，但不含 odd lot[官方] | 逐笔 `Last`（秒级时间），或 RT Volume（毫秒时间，颗粒度较低）[官方] |
| 在本包中的用途 | 参照报价、升舱触发 | 核心 | 理解订单簿变化的伴随证据 |

### 2.2 交易员的七个问题

| 交易员的问题 | 本包提供的可观测信号 | 需要模型权衡的解释 |
|---|---|---|
| 这个价位的挂单是真的吗？ | 挂单集中处的存续时长；价格靠近时是否撤出；有没有同场所成交 | 真实供给、短暂挂单、做市商调整报价 |
| 突破是真的吗？ | 卖方带内量下降；同场所成交覆盖率；穿越档数；穿越后是否迅速补单；成交速率 | 主动买盘吃单、卖方撤单后价格上移、上方还有隐藏卖单 |
| 有人在这里承接吗？ | 同价成交远超显示量；显示量反复恢复；价格没有穿越 | 冰山单或保留单、odd lot 或中间价成交、多个参与者轮流补单 |
| 流动性在变差吗？ | 价差和带内深度相对自身基线的比值；空档；更新速率 | 时段效应（开盘、午间）、消息公布前撤单、波动上升 |
| 买卖压力偏向哪一边？ | 最优档失衡、OFI、多档 OFI，以及各自的持续时长 | 真实压力、单一大单造成的形状变化、更优价挤出旧档 |
| 进场或出场要付出多少？ | 静态冲击（覆盖量、未覆盖量、覆盖部分均价、相对参照的差额）；同价已观察量；止损区支撑量 | 隐藏流动性会让实际成本更低；显示量在下单时被撤走会让成本更高 |
| 盘口还能代表市场吗？ | 可见簿最优价与报价参照的一致性；场外成交占比 | 覆盖场所之外有更优报价；成交主要发生在场外 |

### 2.3 能力边界

- **看不到**：
  - 隐藏单和冰山单的保留部分；
  - 未订阅场所的订单簿（本账户为 NYSE、NYSE Arca、Cboe BZX、NASDAQ BX）；
  - 场外成交背后的订单；
  - odd lot 挂单[官方]；
  - 订阅之前的订单簿（TWS API 没有历史深度接口）。
- **没有**：订单 ID、深度更新的源端时间戳、成交的主动方[官方]。
- **不推断**：参与者身份（MPID 不等于最终客户）和意图（撤单不能直接定性为幌骗）。

所以 L2 给出的是证据，不是结论。本包负责把证据度量准确、标清边界，推理交给模型。

### 2.4 与 pi-technical 的分工

pi-technical 回答“在哪里”：价位、趋势和 E0–E6 事件。本包回答“此刻那里发生了什么”。

组合方式有两种：模型把 `technical_context` 返回的价位登记成本包的价格带（§9.4），或者在 read 时临时传入。两个包不互相导入代码，不共享连接，各自使用独立的 clientId。

## 3. 数据输入

### 3.1 本账户的 L2

| 订阅 | API 深度 | v2 的处理 |
|---|---|---|
| NASDAQ TotalView-OpenView + EDS（加 Network A/B/C） | 满足 IBKR 列出的 API 条件[官方]；直连时带 MPID | 核心来源 |
| IEX Depth of Book | 已订阅，但公开页面没写 API 条款；第三方转述的 2152 通知列出了 IEX[实盘] | 核验后并入 |
| ICE Futures US（Digital Asset、Gold and Silver）L2 | 定价页标为 “(L1, L2) Fee Waived”[官方]；覆盖哪些合约未公开；需要期货交易权限[官方] | 设计上支持任意证券类型，核验后启用 |
| US and EU Bond Quotes L2 | 覆盖范围未公开 | 同上 |
| NYSE OpenBook、ArcaBook、Cboe BZX、NASDAQ BX | 未订阅 | 这些场所的订单簿不可见，写入能力标志 |

本包按合约设计，不限定证券类型：期货、债券只要深度可用就能接入。场外成交占比这类股票专属指标只对股票计算。

### 3.2 输入流与层级

| 输入 | IBKR 请求 | 提供什么 | 占用 | 默认 |
|---|---|---|---|---|
| 深度（SMART） | `reqMktDepth`，isSmartDepth=True | 已授权场所的聚合订单簿，`marketMaker` 为交易所[官方] | 1 个深度请求 | 默认模式 |
| 深度（直连） | `reqMktDepth`，指定 ISLAND 或 IEX | 单一场所的订单簿；NASDAQ 带 MPID[官方] | 1 个深度请求（同一标的开多个请求时怎样计数[实盘]） | 需要看 MPID 时 |
| 报价参照 | `reqMktData`，实时 | 顶层报价，美股按 250ms 快照更新[官方]；是否为综合报价口径需核实 | 1 条行情线 | 默认开启；也是 RT Volume 和升舱的基础 |
| 成交（完整） | `reqTickByTickData`，Last | 每笔成交的价格、数量、交易所、特殊条件，秒级时间[官方] | 1 路逐笔（行情线数的 5%）[官方] | tape=tbt |
| 成交（轻量） | `reqMktData` 通用 tick 233（RT Volume） | 价格、数量、毫秒时间戳（官方示例）、当日总量、VWAP；没有交易所和成交条件；颗粒度低于逐笔[官方] | 复用报价的行情线，不额外占用 | tape=rt |
| 精确报价（可选） | `reqTickByTickData`，BidAsk | 逐笔买卖报价 | 1 路逐笔 | 默认关闭，执行场景按需开启 |

`tape` 参数的取值：
- `auto`：有逐笔名额时用 `tbt`，没有就用 `rt`。实际层级写在每条输出里；层级切换会开启新的成交数据段，不与旧段拼接。pinned 和 task 订阅默认使用 `auto`。
- `tbt`：只用逐笔；没有名额就报错，不会被自动降级。
- `rt`：临时订阅的默认值，不消耗逐笔名额。
- `off`：不订阅成交流。

需要成交场所的指标（例如同场所覆盖率）在 `rt` 层级下不可用，输出中会写明原因。

### 3.3 能力标志

每个标的的每条输出都带能力标志：

| 标志 | 取值 |
|---|---|
| `depth_mode` | smart，或 direct:场所 |
| `venues_observed` | 实际出现过的场所 |
| `attribution` | exchange、mpid 或 none |
| `quote_scope` | consolidated_verified 或 unverified |
| `tape_tier` | tbt、rt 或 off |
| `size_unit` | 按流分别记录，核实前为 null |
| `tick_rule` | market_rule 或 none |
| `prefix_semantics` | verified 或 unverified |

特征和 watch 条件是否可用，由这些标志决定。

### 3.4 单位、价格、时间

- **单位**：深度、逐笔、RT Volume、报价各自核实。官方说明美股 RT Volume 的成交量按手（lot）报告，量为 0 通常表示 odd lot[官方]，可见同一账户的不同流单位可能不同。核实之前：同一流内的比例（如失衡、相对变化）可以使用；股数、金额、跨流比较和静态冲击都不可用。
- **价格**：
  - 内部用 Decimal，跨进程用十进制字符串。
  - 价格距离优先按 market rule 换算成 tick 数：用 `reqContractDetails` 返回的 marketRuleIds 调用 `reqMarketRule`[官方]；换算不了就用价格差和 bps。
  - 不用 minTick 推算 tick，因为它只是所有场所、所有价位中的最小步长[官方]。
- **时间**：
  - 订单簿用本地接收时间。输出使用纳秒格式，但不代表纳秒精度。
  - 逐笔成交的时间精确到秒[官方]；RT Volume 为毫秒时间戳。
  - 报价按字段分别记录接收时间，因为价格不变时可能只更新数量[官方]。
  - 另外记录从回调到处理完成的积压时间，但不把它当作交易所延迟。

## 4. 容量：不写死标的数

### 4.1 为什么不需要写死

IBKR 的限制客观存在，但会随账户变化[官方]：
- 深度名额按行情线数分档：100–400 条对应 3 个，401–500 条对应 4 个，依此类推，1100 条以上对应 11–60 个。每个 Quote Booster（USD 30/月）另加 1 个。
- 行情线数取三者中的最大值：月佣金 ÷ 8、权益 × 100 ÷ 1,000,000、100。TWS 观察列表和所有 API 连接共用这些行情线。
- 逐笔成交名额是行情线数的 5%。

本包不需要知道具体数字：请求被接受就用；被拒绝（309、101 或逐笔名额错误）就按 §4.2 处理。账户买了 Quote Booster 或行情线增加以后，下一个请求会直接成功，不用改代码或配置。

### 4.2 四级优先级

| 级别 | 如何产生 | 自动回收 | 典型用途 |
|---|---|---|---|
| pinned 固定 | 用户或模型显式 subscribe | 从不 | 主要交易标的 |
| task 任务 | 有 watch 或订单上下文依赖该标的 | 从不；依赖解除后降为 ephemeral | 盯关键价位、管理持仓 |
| promoted 升舱 | 观察清单中的标的接近关键价位时自动申请 | 离开接近区超过驻留时间后释放；可被更高级别抢占 | 多标的轮动盯盘 |
| ephemeral 临时 | `orderbook_read` 隐式订阅 | 空闲超过 TTL（[初值] 10 分钟）后释放；可被更高级别抢占 | 临时看一眼 |

名额被拒时的处理（合成校验 test_12）：
1. 只从比新请求低的可回收级别里选：先选 ephemeral，再选 promoted；同一级别选最久未用的。
2. 取消选中的订阅，按请求节奏重试一次，并在结果里写明“为腾出名额释放了某个标的”。
3. 找不到可回收的订阅时，返回 `depth_capacity_rejected`，附上券商原文和本包当前持有的订阅，由模型或用户决定释放哪个。
4. pinned 和 task 永远不会被自动回收。

逐笔名额同理：只有设为 `tape: "auto"` 的标的，才会在优先级更高的标的需要名额时从 `tbt` 改为 `rt`，并披露这次切换。

### 4.3 按需升舱

交易员平时看 L1 列表，价格靠近计划价位时才调出 L2 窗口。本包把这个做法程序化：
- **观察清单**：每个标的只订阅报价参照，占 1 条行情线。可以登记关键价位（来自 pi-technical、用户或模型）和接近阈值（价格差、bps，或模型换算好的 ATR 倍数）。
- **升舱**：价格进入某个价位的接近区并停留 ≥ 5 秒（[初值]），且有名额（或能回收更低级别）时，自动申请深度。逐笔名额按 §4.2 的策略分配。
- **降舱**：价格离开接近区（带滞回）≥ 120 秒（[初值]），且没有 watch 依赖时释放。
- **披露**：升舱后的数据从申请时刻开始。输出会写明“深度自某时刻起观察”，预热不足的指标标为不可用。
- **名额不够**：升舱请求按 §4.2 处理，不影响 pinned 和 task。

### 4.4 本地资源准入

- 不设标的数上限，以实测负载为准：reducer 积压的 p95、CPU、各类内存字节预算（§13.1）。
- 超过准入阈值时，新订阅返回 `local_capacity_exhausted` 并说明当前负载。已有订阅不受影响；不会静默减少行数，也不会切换来源。
- 提供可选软上限 `PI_ORDERBOOK_MAX_SYMBOLS`，默认不设，供想控制成本的部署使用。

### 4.5 状态披露

- 状态只报告三类信息：本包持有的各级订阅、每个流的层级、最近一次券商拒绝（消息码、时间、请求）。不显示猜测出来的账户总额。
- TUI 状态栏示例：`L2 AAPL● NVDA◐ TSLA○ · depth 3（14:02 收到 309）· TBT 2 · RT 1 · watch 4 · 唤醒 3/12h`。其中 ● 表示已预热，◐ 表示预热中，○ 表示数据陈旧。

## 5. 架构

### 5.1 进程与组件

```text
┌───────────────────────────── Pi 进程 ─────────────────────────────┐
│ pi-orderbook extension (TypeScript)                                 │
│  工具  orderbook_read / orderbook_details / orderbook_control         │
│  命令  /orderbook    模板 /ob-*    skill order-book-analysis           │
│  Controller：意图（Pi 分支状态）· 投递（预算、紧急度、跟踪）· 生命周期   │
│  Signals：pi.events "pi-orderbook/signal.v1"    UI：状态栏、盘口（TUI） │
└────────────────┬───────────────────────────────────────────────────┘
                 │ NDJSON：请求/响应、唤醒候选、状态（不传逐条行情回调）
┌────────────────▼──────────── Python worker ──────────────────────────┐
│ IB 适配层（官方 ibapi 10.50.2，单连接，独立 clientId）                   │
│ Reducer（唯一写入者，按序处理行情、定时器、控制命令）                     │
│   CapacityManager：四级优先级 · 升舱/降舱 · 成交流层级 · 准入            │
│   每个标的：RawBook · QuoteRef · Tape · Features · Patterns          │
│   WatchEngine：条件判定（三值逻辑）· 状态机 · 注意力过滤                 │
│ EvidenceStore：历史 checkpoint/增量 · 采样 · 价格带积分 · ViewStore     │
│ Recorder（可选，仅本地）                                               │
└────────────────┬───────────────────────────────────────────────────┘
                 ▼
        IB Gateway / TWS（与 pi-technical 共用，clientId 不同）
```

分工：
- **Python worker** 拥有全部市场事实：订单簿、报价、成交、特征、模式、watch 条件判定、冻结证据、容量管理。
- **TypeScript extension** 负责与模型有关的一切：观察意图的持久化（作为 Pi 分支状态）、唤醒投递与预算、消费跟踪、生命周期、UI。
- **意图同步**：意图的权威副本在 Pi 会话里。extension 启动或切换分支后，把意图下发给 worker，worker 回报判定结果。
- 两边不重复计算金融指标，也不各自维护订单簿。

### 5.2 热路径

- ibapi 回调只记录本地接收时间和全局序号，然后入队。唯一的 reducer 按顺序处理行情、定时器和控制命令。
- 特征和 watch 条件增量更新。定时器事件也进入同一队列，用来结算“没有新事件、但时间在流逝”的状态。
- 需要重放历史的 details 请求在单独线程里对冻结数据计算，不阻塞 reducer。
- 回调里不做 JSON 序列化、全历史扫描，也不调用模型。

### 5.3 进程间协议

- **帧格式**：NDJSON，每帧带 `protocol_version`、`run_id`、`request_id`、`type`，单帧上限 1 MiB。
- **校验**：TS 端用 TypeBox 严格校验，沿用 pi-technical 的做法：拒绝非有限数字，校验 run_id 和版本。
- **数值**：价格和数量用十进制字符串，比例用有限 number。
- **主动推送**：worker 只推送状态、容量变化、唤醒候选和质量事件，不推送逐条行情回调。
- **取消与迟到**：调用方放弃等待不等于取消行情；迟到的合法响应识别后丢弃，不会导致 worker 崩溃。

## 6. 订单簿与证据引擎

### 6.1 原始行与价格档

- **按 position 更新**：每个深度请求、每一侧维护一个行数组，按官方回调语义更新[官方]：
  - insert：在 position 处插入，后面的行后移；
  - update：替换该行；
  - delete：删除该行，后面的行前移。

  先按 position 更新，再按价格聚合成档，并保留交易所或 MPID 构成。
- **核验前的处理**：满行后顶端插入时尾部怎样处理、同价多行怎样排列，都要按模式在实盘核验（附录 B）。核验前，该模式照常显示原始行，但关闭依赖前缀语义的可比较性判定（§6.3）。
- **异常**：position 越界或出现未知操作时，隔离并重建该请求。跨场所的锁定或交叉报价则保留事实，暂停依赖正常双边市场的计算，不当作数据损坏。
- **零数量行**：保留为回调事实，但不计入可见流动性。

### 6.2 连续性

| 情况 | 原始簿 | 观察段与历史 |
|---|---|---|
| 行进出前 N 行 | 增量维护 | 连续；触及尾部的价格带暂停可比统计 |
| 317 重置[官方] | 先清空再应用新条目 | epoch + 1，持续性重新计时；旧 view 仍是有效历史 |
| 316 暂停、1101 恢复但数据丢失[官方]、重订阅、已知本地丢失 | 新请求身份，新 epoch | 不与旧段拼接 |
| 1102 恢复且数据保留[官方] | 保留 | 把断连期间记为未知间隔，不用旧簿填补 |
| 长时间没有更新 | 不视为损坏 | 披露最后接收时间；暂停时效敏感的判定 |
| 取消后的迟到回调 | 丢弃（reqId 不复用） | — |

正常重置只说明当前数据链路需要重建，不撤销此前有效的观察。只有确认某段数据已损坏时，才对受影响的 view 和唤醒发出更正（P10），并注明受影响的时间范围。

### 6.3 可比较性判定

只有当一段价格完全落在本次请求已返回的视图内时，价格带的总量才有意义。判定规则如下（合成校验 test_01–04）：

```text
前提：该模式的排序与尾部语义已核验；该侧可用；没有已知丢失；请求、单位、窗口未改变。
记号：该侧已返回的正数量行按最优到最差排序，最差价为 worst；请求行数 N；实际行数 n。

ask 侧，目标带 [L, U]：
  已核验“行数不足即全侧”且 n < N   → determined_in_view（总量 = 带内观察量，可以为 0）
  否则若 U < worst                  → determined_in_view
  否则若 L ≤ worst                  → partial_at_tail（只给观察量，总量未知）
  否则                              → beyond_view（未知）

bid 侧对称：L > worst → determined_in_view；U ≥ worst → partial_at_tail；否则 beyond_view。
```

说明：
- **优于最优价的区域**：这里在视图内一定没有挂单，所以卖方带整体低于最优卖价时，结果是 determined，量为 0。这修正了 v0.3 的缺口。例如卖方参考带被突破后，问“这段卖单还在吗”，正确答案是“可见盘口上已经没有了”，而不是“未知”。
- **最差价作保护行**：价格带触及最差价时，同一价位可能还有没返回的行，所以只给观察量。
- **“行数不足即全侧”**：依据官方说明“订单簿不足请求行数时只返回现有条目”[官方]。但初始化期间行是陆续到达的，所以要先核验，并等首批数据稳定后才启用。
- **范围**：`determined_in_view` 只说明“在本请求覆盖的场所和返回范围内”，不等于全市场。SMART 模式下，判定对整个返回集合成立，不能据此证明某个单一场所自己的带内总量。

### 6.4 时间有效性

```text
T_valid            = ∫ v(t) dt
Q_time_weighted    = ∫ v(t)·Q(t) dt / T_valid
condition_fraction = ∫ v(t)·1[condition(t)] dt / T_valid
coverage_fraction  = T_valid / 窗口时长
```

- v(t) 表示该指标在 t 时刻是否有效（数据可用、可比较、没有缺口），Q(t) 是数量。分母为 0 时输出 null。
- 同时报告最长连续段和当前连续段，缺口既不删除也不拼接（test_08）。持续时长来自状态保持时间的积分，不来自回调次数，也不用每秒采样去证明“中间没有中断”。
- 10s、60s、300s 是查询窗口，不要求每项功能都等满 300 秒；窗口未满时报告实际覆盖的时长。

### 6.5 历史与冻结 view

| 保存对象 | 目标[初值] | 支持什么 |
|---|---|---|
| 盘口 checkpoint 加有序增量、报价更新、成交记录 | 每个标的最多 300 秒，受全局字节预算约束 | 在冻结 view 上重放任意价格带的变化过程 |
| 已登记价格带的事件驱动积分 | 自登记起最多 60 分钟 | 关键价位的长时持续性与有效覆盖 |
| 每秒特征采样 | 60 分钟 | 概览；作为相对基线的分母 |
| 模式和 watch 状态日志 | 字节上限 | 复盘、唤醒依据 |

- **多标的同一时刻**：view 在一个全局序号 `cut_seq` 上冻结所有相关标的，所以一个 view 可以包含多个标的，并在同一时刻比较它们。
- **只读冻结数据**：冻结时 pin 住已封存的历史块，并复制可变的尾部。details 只能读这些数据，不能读实时缓存（v0.3 的做法）。
- **当时可知**：`cut_seq` 之后才收到的数据不进入旧 view，即使是源端时间更早的成交也一样（test_13）。
- **预算不足**：可以创建一个明确缩短了历史的 view，并在摘要里说明。view 一旦创建，内容不再变化；确实无法保留时返回 `view_expired`，不会换成最新数据。
- **历史范围披露**：所有历史类输出都给出 `available_from`、`available_to`、分辨率、缺口和截断原因。

## 7. 特征与可观测模式

### 7.1 特征目录

以下特征都属于“推导”级：确定性计算，附带定义、单位、窗口、可比较性和可用性。

| ID | 定义 | 条件与说明 |
|---|---|---|
| `spread` | 最优卖价 − 最优买价，另给 bps 和 tick 数 | 视图内价差，不是 NBBO；tick 数需要 market rule |
| `mid`、`weighted_mid` | 两价平均；按对侧顶档量加权的价格 | weighted_mid 是描述量，不是校准过的 micro-price |
| `imbalance_l1` | (Qb1 − Qa1) / (Qb1 + Qa1) | 即 queue imbalance[Gould & Bonart] |
| `imbalance_band` | 同一价格距离内两侧观察量之差除以之和 | 两侧都需 determined |
| `depth_profile` | 按距离（bps 或 tick）累计的两侧观察量 | 需 determined |
| `concentration` | 显示量显著高于邻近价位中位数的价位，附首次出现时间、存续时长、场所构成 | 描述“挂单集中”，不称为支撑或阻力 |
| `holes` | 视图内连续没有挂单的价格区间 | 仅限视图内 |
| `level_lifetime` | 近端价位显示量的存续时长分布（中位数、短命占比） | 衡量短暂挂单（fleeting orders）的程度[Hasbrouck & Saar] |
| `update_rate` | 每秒行更新次数 | 反映活跃度，也用于负载监测 |
| `ofi_l1` | 最优档订单流失衡 Σeₙ，可按顶档平均深度归一 | 公式见下，来自 CKS 2014；test_05 |
| `mlofi` | 前 K 档各自的 OFI 组成的向量 | 需前 K 档 determined[Xu, Gould, Howison] |
| `regime` | spread、带内深度分别除以本时段的滚动中位数 | 需观察 ≥ 300 秒[初值] |
| `price_agreement` | 可见簿最优价与报价参照相等的有效时间占比 | 价格一致不代表数量覆盖 |
| `band_dynamics` | 固定价格带的起止量、极值、时间加权量、有效覆盖、最长连续段 | test_08 |
| `print_coverage` | 带内下降量中，被同场所、同价带、同窗口成交覆盖的比例；另报非视图场所在该价带的成交量 | 需 `tbt`；test_06 |
| `prints_vs_display` | 同场所某价的成交量减去该价在窗口内的最大显示量；大于 0 表示成交超过显示 | 需 `tbt` |
| `replenishment` | 同价在同场所成交后，显示量恢复的次数 | 需 `tbt` |
| `traversal` | Δt 内价格穿越的价位数、其中有成交的价位数、被移除的档 | 需成交流 |
| `tape_stats` | 笔数、成交量、VWAP、场所构成、场外占比（交易所代码核实后）、成交速率 z 值 | `rt` 层级没有场所字段 |
| `scenario` | 静态冲击：覆盖量、未覆盖量、覆盖部分均价、末档价、相对参照的差额 | 单位核实前不可用；test_07 |

OFI 的单步增量（Cont, Kukanov, Stoikov 2014）如下。P 为最优价，q 为该价挂单量，上标 b 表示买方、a 表示卖方：

```text
eₙ = 1{Pᵇₙ ≥ Pᵇₙ₋₁}·qᵇₙ − 1{Pᵇₙ ≤ Pᵇₙ₋₁}·qᵇₙ₋₁ − 1{Pᵃₙ ≤ Pᵃₙ₋₁}·qᵃₙ + 1{Pᵃₙ ≥ Pᵃₙ₋₁}·qᵃₙ₋₁
```

### 7.2 可观测模式 P1–P10

- 模式对所有已订阅标的持续检测，结果出现在 read 和 details 中；是否唤醒模型由 §8 决定。
- 名称只描述看得到的现象，原因留给模型判断。
- 阈值都相对该标的自身的基线，均为[初值]。

| ID | 模式 | 可观测定义 | 事实字段 | 模型要权衡的解释 |
|---|---|---|---|---|
| P1 | 带内显示量下降 | 已登记或自动识别的价格带（determined），时间加权量在 W 秒内下降 ≥ r | 前后量、最低量、`print_coverage`、价格相对位置、之后是否补回 | 成交消耗、撤单、两者并存 |
| P2 | 挂单集中变化 | `concentration` 出现、存续达标或消失 | 存续时长、消失时与价格的距离、同场所成交、附近是否出现相近数量 | 真实供给、短暂挂单、移价 |
| P3 | 多档穿越 | Δt 内价格穿越 ≥ m 个价位，其中 ≥ m' 个有成交 | 穿越档数、成交量、方向、之后是否补单 | 主动扫单、薄区滑移 |
| P4 | 成交下补单 | 同价成交 ≥ β × 平均显示量，补单 ≥ n 次，价格没有穿越 | 成交量、显示量均值和峰值、补单次数、持续时间 | 冰山单或保留单、多个参与者轮流补单、odd lot |
| P5 | 流动性状态变化 | spread 或深度相对基线越过阈值并持续 | 比值、持续时间、两侧对比 | 时段效应、消息公布前撤单、波动上升 |
| P6 | 失衡持续 | `imbalance_band` 或累计 OFI 越过阈值并持续 | 数值、持续时间、两侧深度 | 真实压力、单一大单的形状效应、更优价挤出旧档 |
| P7 | 成交加速 | 10 秒成交速率 z 值 ≥ k | 速率、成交量、价格区间、场所构成 | 消息、算法执行、止损触发 |
| P8 | 盘口与报价背离 | 报价参照的最优价在可见簿之外，并持续 | 价差、持续时间、发生在哪一侧 | 覆盖场所之外有更优报价、采样时差 |
| P9 | 成交超过显示 | `prints_vs_display` 在窗口内 > δ | 超出量、价位、场所 | 隐藏单或保留单、odd lot、中间价成交 |
| P10 | 数据质量事件 | 317、316、1101、1102、积压超限、覆盖变化、单位或层级变化 | 受影响的标的和时间段，对活跃 watch 和 view 的影响 | — |

与旧版本的关系：
- v1 的 D1–D6 改成了只描述现象的 P1–P9。原来的 consumed、pulled、absorption 标签不再由程序输出，由模型根据事实字段自行判断。
- v0.3 唯一的提醒规则 `band_quantity_drop` 就是这里的 P1。

### 7.3 推断指标（默认关闭）

- `aggressor_quote_test`：只针对成交场所属于视图场所的成交，用接收时刻可见簿的最优价判断主动方向，同时输出匹配率和模糊率。
- `bvc_imbalance`：bulk volume classification（BVC）[Easley, López de Prado, O'Hara 2012]，按成交柱的标准化价格变化拆分买卖量。它不依赖报价时序，但仍然是估计。

这两项在 read 和 details 中标为“推断”，并附可靠性统计。默认不能作为 watch 条件；开启 `allow_inferred_conditions` 后可以使用，唤醒消息会注明“基于推断指标”。

## 8. 唤醒：程序怎样叫醒模型

### 8.1 唤醒来源

| 来源 | 定义者 | 例子 | 何时生效 |
|---|---|---|---|
| watch（观察计划） | 模型或用户，通过 `orderbook_control` 登记 | “231.00–231.05 卖方带内量降到登记时的三成以下，且成交覆盖率 ≥ 0.6 时叫醒我” | 登记后立即生效 |
| 订单上下文条件 | 登记订单、止损、目标价后自动派生 | “止损 229.80 下方 5 bps 内的买方观察量低于基线的四成” | hybrid、execution profile 下默认生效 |
| 内置模式 P1–P9 | 包内置，按 profile 选择 | 关键价位附近出现 P3 穿越 | 以某个 profile 开始盯盘后生效；只做一次读取时不唤醒 |
| 质量事件 P10 | 包内置 | 活跃计划依赖的数据发生重置 | 只在影响活跃 watch 或已投递的 view 时 |

### 8.2 watch 条件语言

条件语言是封闭、有类型、有上限的声明式结构，不是通用表达式语言。

- **叶子条件**：比较目录中的一个指标（完整清单在 skill references 中），比较方式有五种：
  - `value`：与绝对值比较；
  - `change_from_arm`：与登记时的值比较，数值为 (当前值 − 登记时值) / 登记时值；
  - `baseline_ratio`：与本时段滚动中位数比较，数值为 当前值 / 中位数；
  - `crosses_above`、`crosses_below`：向上或向下穿越；
  - `pattern`：某个模式 P1–P9 发生，可以附过滤条件。
- **组合**：只有 `all` 和 `any`；嵌套不超过 2 层，叶子不超过 6 个（test_09）。
- **三值逻辑**：指标的前置能力不满足时（例如价格带不是 determined、成交流不是 `tbt`、单位未核实），叶子取“未知”。
  - `all`：有假即假，全真才真，其余为未知。
  - `any`：有真即真，全假才假，其余为未知。
  - “未知”永远不会触发：它会中断持续计时，并让 watch 显示为 `suspended_data`。
- **状态机**（test_10）：`armed → pending（持续 hold_s）→ 触发 → cooldown → armed`。
  - 回到 armed 需要同时满足：冷却期已过；`exit_when` 成立（没写 `exit_when` 时，要求 `when` 变为假）。这样持续成立的条件不会反复触发。
  - 终止状态还有三种：`expired`（到期）、`done`（达到 `max_fires`）、`cancelled`。
- **记录**：每次状态迁移都记录当时的指标值，供唤醒消息和 `details(section: "watches")` 使用。
- **数量上限**：由字节和 CPU 预算决定，不写死。判定在 reducer 中随相关更新增量进行，并由定时器补足。

指标目录（节选）：

| 指标 | 参数 | 前置能力 |
|---|---|---|
| `price.last`、`quote.bid`、`quote.ask`、`quote.mid` | — | 报价参照 |
| `book.best_bid`、`book.best_ask`、`book.spread_bps` | — | 深度 |
| `band.qty` | band_id | 价格带为 determined |
| `band.print_coverage`、`band.prints` | band_id、window_s | `tbt` 层级；在 `rt` 层级下 `band.prints` 不做场所过滤，并加以标注 |
| `depth.within` | side、bps 或 ticks | determined；使用 ticks 需要 market rule |
| `imbalance.l1`、`imbalance.band` | 价格距离 | 深度；band 还需 determined |
| `ofi.l1` | window_s | 最优档连续 |
| `tape.rate_z`、`tape.volume` | window_s | 成交流 |
| `regime.spread`、`regime.depth` | — | 已观察 ≥ 300 秒[初值] |
| `order.level_qty`、`stop.support_qty` 等 | order_id | 订单上下文（§10.2） |

### 8.3 内置模式的注意力过滤

内置模式可能很多，需要像交易员一样过滤噪声。每个模式事件都计算一个可解释的显著性分数：

```text
salience = relevance × magnitude × novelty × quality
relevance ：触及已登记价位或订单上下文 = 1；距当前价 ≤ X bps = 0.6；其他 = 0.3   [初值，profile 可调]
magnitude ：关键统计量在该标的本时段已观测分布中的分位；预热不足时上限为 0.5
novelty   ：冷却期内同类模式在同一价区重复出现 = 0，否则 = 1
quality   ：可比较性不是 determined，或数据陈旧 = 0，否则 = 1
```

- 分数达到 profile 设定的阈值（[初值] 0.5）才成为唤醒候选。
- 四个分量原样写进唤醒消息，模型能看到“为什么叫醒我”。
- 模型自己登记的 watch 不经过这层过滤，只受预算约束。

### 8.4 投递到 Pi

Pi 的 `sendMessage` 在源码中的行为如下[官方，`core/agent-session.js`]：
- agent 运行中：设了 `followUp` 的消息进入 follow-up 队列；其余情况按 steer 处理，在当前轮工具执行完、下次调用模型前送达。
- agent 空闲且 `triggerTurn: true`：立即开始新一轮。
- `nextTurn`：先挂起，随用户下一条消息注入。

本包按紧急程度映射到这些行为：

| 紧急程度 | agent 空闲 | agent 正在运行 |
|---|---|---|
| urgent | `triggerTurn: true`，立即开新一轮 | `deliverAs: "steer"`，插入当前运行 |
| normal | `triggerTurn: true`；发送前重新取证，并复核条件仍然成立 | 本包暂存，等空闲且没有排队消息时再发，以便发送时还能复核新鲜度；超过 TTL 就丢弃并记录 |
| ambient | `deliverAs: "nextTurn"`，随用户下一条消息附带 | 同左 |

- **无人值守部署**（RPC 或 SDK 宿主，没有用户消息）：ambient 改为低频摘要，按 normal 投递，使用单独的预算。
- **预算**（test_11）：以下各项均可配置：
  - normal 每小时次数（[初值] 12）；
  - urgent 每小时次数（[初值] 6）；
  - 最小间隔（[初值] 20 秒）；
  - 合并窗口（[初值] 30 秒）；
  - 候选上限（[初值] 16）。

  urgent 只能来自标为 urgent 的 watch 或订单上下文条件。
- **消费跟踪**（沿用 pi-technical）：
  - `message_start` 中 customType 和 details 匹配，即确认已消费；
  - `agent_before_settle` 记录本轮结果；
  - `agent_settled` 时释放 view 的 pin。

  本轮失败或被中断时不自动重发；watch 保留，并标记 `last_delivery_failed`。
- **与 pi-technical 并存**：两个包各有预算。normal 投递会等到没有排队消息，不会与 L1 的研究消息堆叠；urgent 可以插入。

### 8.5 唤醒消息

内容控制在 4 KB 以内，模型不用重读 skill 也能看懂要点。示例（数值只是示意，不是真实行情）：

```text
[pi-orderbook] 唤醒 · normal · watch w7「突破确认」于 14:31:07.412Z（本地接收）触发
你的备注：若 231.00–231.05 卖方被成交消耗且价格站上 231.05，考虑延续；若量被撤而无成交，警惕假突破。
条件：band.qty(r1) 较登记时 −79%（4,200 → 900，持续 2.4s）且 band.print_coverage(r1, 60s) = 0.94 → 成立
证据（view 9f3c…，cut_seq 88121，SMART：NASDAQ、IEX，tape=tbt，单位=待核实）：
- 带内同场所成交 3,100；非视图场所同价带成交 1,800
- 最新成交 231.06，高于价格带；231.06–231.10 卖方观察量为 30 分钟中位数的 0.4 倍
- 10 秒成交速率 z = +3.1；可比较性 determined_in_view；无缺口
需要权衡：显示量被成交消耗，还是撤单与隐藏单或 odd lot 成交同时发生；穿越后是否迅速补单（见 skill patterns P1、P3）
继续读取：orderbook_details(view_id, target="AAPL", section="levels" 或 "tape" 或 "execution")
```

消息的 `details` 字段带 `run_id`、`view_id`、`watch_id`、`state_seq`，只用于消费跟踪，不发给模型。

### 8.6 程序化消费者

watch 触发和达到阈值的模式会同时发到 Pi 的进程内事件总线，执行包等程序可以实时订阅，不必等模型：

```json
{"schema": "pi-orderbook/signal.v1", "target": "AAPL", "con_id": 265598, "kind": "watch_fired", "id": "w7", "urgency": "urgent", "fired_at": "2026-09-28T14:31:07.412Z", "cut_seq": 88121, "view_id": "9f3c1a2b7d4e5f60", "facts": {"band_id": "r1", "change_from_arm": -0.79, "print_coverage": 0.94}, "comparability": "determined_in_view", "tape_tier": "tbt"}
```

- 频道名带版本号。Pi 事件总线的 payload 没有类型约束[官方]，接收方必须自己校验。
- 信号只包含推导级事实，不包含指令。执行包按自己的预授权规则和风控决定是否行动。

## 9. 主动调用：让每次调用都有价值

### 9.1 工具

| 工具 | 执行方式 | 职责 |
|---|---|---|
| `orderbook_read` | sequential（可能建立订阅） | 确保目标已订阅，必要时建立临时订阅并等待首批数据（`wait_ms` ≤ 5000）；在同一个 `cut_seq` 冻结一个 view（可以包含多个标的）；返回面向推理的摘要 |
| `orderbook_details` | parallel（只读） | 读取指定 view 的某个栏目，或在冻结数据上计算 |
| `orderbook_control` | sequential | 订阅、观察清单、价格带、watch、订单上下文、profile、提醒与预算、录制、状态、停止 |

- 三个工具都提供 `promptSnippet`。工具描述里写明副作用（会订阅行情、会持续观察、会录制），并写入 skill 的绝对路径、要求先读 skill（沿用 pi-technical）。
- 参数用 TypeBox 严格校验。业务错误直接 throw；数据缺失不算错误，用可用性字段表达。
- 部分标的订阅失败时，其余标的照常返回，失败的标的附上原因。
- `/orderbook` 命令调用同一个 controller，供人类用户使用。

### 9.2 read 的摘要

单个标的时，摘要按模型推理的顺序组织：
1. **身份与口径**：标的、`cut_seq`、profile、能力标志（覆盖场所、报价口径、成交流层级、单位），以及各指标的预热情况。
2. **此刻**：两侧前 5 档（按价聚合，附场所或 MPID 构成）、spread、`imbalance_l1`、`depth_profile`，都附上相对本时段中位数的比值。
3. **刚刚发生了什么**（10s、60s、300s）：OFI、regime、update_rate、挂单集中的变化、成交统计、近期模式。模式按显著性排序，每一项同时给出对侧证据，避免只看一边。
4. **你的计划**：已登记价格带的状态；每个 watch 的状态，以及距离触发还差多少；订单上下文（hybrid、execution 下）。
5. **数据质量与限制**。
6. **建议补读**：例如“P1 发生在 r1，可读 levels 和 tape 核对覆盖率”。

多个标的时返回 board：每个标的一行，按显著性排序，外加值得注意的事项。单个标的的细节用 details 的 `target` 参数读取。

输出上限：摘要不超过 16 KiB，details 每页不超过 40 KiB，都低于 Pi 的 50 KB 输出上限[官方]。

### 9.3 details 栏目

| section | 参数 | 输出 |
|---|---|---|
| `ladder` | representation（rows 或 levels）、levels、venue | 原始行或按价聚合的档，附来源和边界状态 |
| `features` | ids、window_s | 所选特征的完整记录：值、单位、窗口、可用性 |
| `levels` | bands（1–8 个）、window_s | 在冻结数据上重放价格带过程：量、可比较性、成交覆盖、补单 |
| `history` | ids 或 band_id、window_s、cursor | 时间序列（从旧到新），注明分辨率和缺口 |
| `tape` | window_s、venue、band、include_excluded、cursor | 成交记录，以及采用和排除的口径；非法值、未解释的特殊条件单独计数 |
| `patterns` | kinds、cursor | P1–P10 记录及事实字段 |
| `watches` | watch_id | 条件、各叶子的当前值、状态迁移日志 |
| `execution` | side、quantity、limit_price、reference、order_id | 静态冲击、同价已观察量、止损区支撑量、相对参照的条件差额 |
| `quality` | — | 请求、深度场所目录与通知原文、实际出现的来源、单位、缺口、历史范围、错误 |
| `board` | cursor | 多标的总览（view 包含多个标的时） |

分页使用不透明 cursor，与 view、栏目、过滤条件绑定。不用秒级时间戳分页，避免漏掉同一秒内的多笔成交。

### 9.4 control 动作

| action | 主要参数 | 行为 |
|---|---|---|
| `subscribe` | target、class（pinned 或 task）、mode（smart 或 direct）、venue、rows、tape | 建立订阅；配置相同时幂等；修改配置需要 `replace: true` |
| `unsubscribe` | target | 释放本包对该标的的订阅；有 watch 依赖时拒绝，并列出依赖 |
| `watchlist` | op（set、add、remove）、items（target、levels、proximity） | 维护观察清单和升舱价位 |
| `band` | op（set、remove）、id、target、side、lower、upper、label、source | 登记关键价格带，从登记时起持续积分 |
| `watch` | op（create、update、cancel、list），以及 §8.2 中的字段 | 管理观察计划 |
| `order_context` | op（set、remove）、id、target、kind、side、price、quantity、note | 登记订单、止损、目标价、计划入场或持仓（§10.2） |
| `profile` | profile、target（可选，按标的覆盖） | 切换角色默认值 |
| `alerts` | enabled、patterns、budget | 内置模式唤醒的开关与预算 |
| `inputs` | target、tape、quote、precise_quote | 调整伴随输入；不重置订单簿 |
| `record` | enabled | 本地录制开关，需要先配置 `PI_ORDERBOOK_RECORD_DIR` |
| `status` | — | 本包状态；不推断账户额度 |
| `stop` | — | 取消全部请求并关闭 worker；幂等 |

每个修改类动作都会在工具结果的 `details` 里返回完整的意图快照（watch、价格带、订单上下文、profile、观察清单），作为 Pi 分支状态保存（§12.3）。

## 10. 角色与场景

### 10.1 profile

| | monitor（盯盘不交易） | hybrid（边盯边做） | execution（只做执行） |
|---|---|---|---|
| 内置唤醒模式 | 已登记价位附近的 P1–P4、P6、P7；P10 | monitor 的全部，加订单上下文条件 | P5、P8；订单与止损价位的 P1、P3；P10 |
| 订单上下文条件的默认紧急度 | — | 止损为 urgent，其余为 normal | urgent |
| read 摘要重点 | 价位行为、变化过程、双向证据 | 两者兼顾 | 执行条件：价差和深度状态、冲击、止损区流动性、同价已观察量 |
| 唤醒消息的任务提示 | 论点是否改变，是否需要调整观察 | 论点是否变化，以及执行条件和风险 | 执行条件是否满足或恶化，风险在哪里 |
| 预算[初值] | normal 12 次/小时 | normal 12 次/小时，urgent 6 次/小时 | normal 6 次/小时，urgent 12 次/小时 |

- **设置方式**：profile 可以全局设置，也可以按标的覆盖，例如 NVDA 只盯盘、AAPL 正在做单。运行时通过 `orderbook_control` 切换；默认值可以用 `--orderbook-profile` 启动参数或 `PI_ORDERBOOK_PROFILE` 环境变量设定。
- **只改默认值**：任何角色都可以显式调用全部能力。

### 10.2 订单上下文

订单上下文由模型或用户声明。本包不读取券商账户的持仓和订单，只基于声明的信息做分析：

| kind | 字段 | 派生指标 | 派生条件（hybrid、execution 下默认） |
|---|---|---|---|
| `resting_limit` | side、price、quantity | 同侧同价已观察量、同侧更优价已观察量、该价成交、距最优价的距离 | 同价显示量快速下降（该价的 P1）、对侧远离 |
| `stop` | side、price、quantity | 止损触发后要成交的一侧在止损价附近的观察量（卖出止损看买方，买入止损看卖方）；按数量的静态冲击 | 支撑量低于基线的阈值比例；价格接近止损且出现 P5 变薄 |
| `target` | side、price | 目标价附近的对侧观察量 | 目标价附近挂单集中出现或消失 |
| `planned_entry` | side、quantity、price（可选） | 执行前静态冲击、流动性状态 | 由模型写 watch |
| `position` | side、quantity | 反向失衡、反向穿越 | 反方向的 P3、P6 |

限制：本包不知道订单实际在哪个场所、处于什么时间优先级，所以只能给出“同价已观察量”，不能给出“我前面还排着多少”。所有数量都只是可见量。

### 10.3 本包为什么不下单

- **单一职责与安全**：下单需要交易权限、独立风控（仓位、亏损、频率上限）、审计和人工确认策略。这些应该集中在专门的执行包里，不应分散在数据包中。
- **本包对交易场景的支持**：
  - 执行分析（§9.3 的 `execution` 栏目）；
  - 订单上下文条件（§10.2）；
  - urgent 唤醒（§8.4）；
  - 给执行包的实时信号（§8.6）。
- **授权留在宿主**：skill 要求模型按宿主赋予的角色表述结论。只盯盘的 Agent 不把输出写成下单指令。有交易授权的 Agent 可以形成交易判断，但要写明证据、条件和风险，并说明静态冲击不是成交保证。

### 10.4 三个场景

**盯盘不交易（monitor）**
1. 开盘前，模型从 pi-technical 取得关键价位，把 8 个候选标的加入观察清单，并登记价位。
2. 盘中价格接近价位时自动升舱。价位附近出现 P1、P3、P4 且显著性达标时，唤醒模型。
3. 模型读取证据，判断论点是否改变，向用户报告，并调整或新增 watch。

**边盯边做（hybrid）**
1. 模型形成入场论点，登记 if-then watch，例如 §9.5 的“突破确认”。
2. watch 触发后，模型读取 `execution` 栏目评估执行条件，把决定交给执行包或用户。
3. 成交后登记止损和目标价（订单上下文）。止损区流动性变薄时发出 urgent 唤醒，插入当前运行。

**只做执行（execution）**
1. 给定母单后，模型持续关注价差和深度状态、静态冲击，选择下单时机和拆分节奏，由执行包具体执行。
2. 止损区或挂单价位的流动性急剧变化时发出 urgent 唤醒。执行包也可以直接订阅 `pi-orderbook/signal.v1`，按预授权规则即时反应。

## 11. Skill 与 prompt 模板：金融理解写在哪里

### 11.1 SKILL.md

```markdown
---
name: order-book-analysis
description: Read and reason about Level 2 order book and tape evidence from pi-orderbook (depth, liquidity, order flow, execution cost, watches and wake-ups). Use for questions about the order book, market depth, Level 2, time and sales, liquidity at a price, breakout or absorption evidence, execution timing, or when a pi-orderbook wake message arrives.
---
```

正文是交易员的读盘流程：
1. **明确问题**：时间尺度（剥头皮、日内、波段），以及宿主赋予的角色。
2. **先验数据**：覆盖场所、报价口径、成交流层级、单位、预热、可比较性、质量事件。数据不够时，先说清楚能判断什么、不能判断什么。
3. **读状态**：看价差、深度、失衡相对自身基线的变化，不看绝对值。
4. **读变化**：哪里变了，有没有同场所成交，价格怎么反应，之后有没有补回。
5. **联系计划**：价位从哪里来（pi-technical、用户、自己的假设），价格带过程是否为 determined。
6. **列假设与竞争解释**（references/patterns.md），找出能区分它们的证据；需要时补读，或者登记 watch 等待。
7. **按角色给结论**：monitor 说明对论点的影响和下一步观察；execution 说明执行条件、风险，以及交给谁执行。任何时候都要说明什么证据会推翻结论。
8. **收尾**：登记或调整 1–3 个 if-then watch 并写好备注，取消过时的 watch。

被唤醒时：先看触发条件和自己当时写的备注，再核对数据质量和新鲜度（必要时重新 read），区分“触发时的事实”和“现在的状态”。

写作规则：
- 事实与解读分开，引用 view_id 和时间。
- 不把可见订单簿称为“市场”。
- 不断言幌骗或参与者身份。
- 使用推断指标时要标明。
- 单位未核实时，不与 L1 的股数比较。

### 12.2 生命周期

| 事件 | 行为 |
|---|---|
| 工厂函数 | 只注册工具、命令、渲染器和事件；不联网、不启动进程[官方要求] |
| `session_start` | 保存 ctx；用 `getBranch()` 重建意图（§12.3）；不继承旧运行时的行情状态 |
| 首次工具或命令调用 | 懒启动 worker 并连接；此时才订阅 active 意图所需的标的 |
| `session_tree` | 从新分支重建意图；旧分支独有的 watch 停止唤醒；清空待投递候选；保留行情订阅和缓冲（行情不属于分支）；ephemeral 仍按 TTL 回收 |
| `message_start`、`agent_before_settle`、`agent_settled` | 投递跟踪；settled 之后释放 manual pin |
| `session_shutdown` | 取消全部请求（`cancelMktDepth` 必须带原请求的 isSmartDepth[官方]），断开连接，结束 worker；幂等 |
| 父进程意外退出 | worker 检测到 stdin EOF 后自行退出 |

### 12.3 分支状态

- **为什么是分支状态**：观察意图（watch、价格带、订单上下文、profile、观察清单）是对话的一部分。在一个分支里制定的计划，不应在另一个分支里继续唤醒模型。
- **存储与重建**：按 Pi 的官方建议，跟随分支的状态存进工具结果的 `details`；在 `session_start` 和 `session_tree` 时，用 `ctx.sessionManager.getBranch()` 重建[官方：extensions.md 的状态一节；官方示例 `todo.ts` 也是这样做的]。
- **恢复策略**：
  - `reload`：视为同一会话，意图恢复为 active，并重新订阅。
  - `resume`、`fork`：按配置 `PI_ORDERBOOK_RESTORE` 处理，默认恢复为 suspended，由模型或用户一次调用重新启用。
  - `new`：不恢复。
- **行情不入会话**：行情数据本身不是分支状态，不写进会话。

### 12.4 运行模式与 UI

| 模式 | 支持 |
|---|---|
| TUI | 全部功能；状态栏和盘口小组件（≤ 4 Hz） |
| RPC、SDK | 全部数据和唤醒功能；无人值守部署应使用这两种模式，由宿主保持进程运行 |
| print、JSON | 进程内的一次性查询；退出时清理，不做持续观察 |

- UI 只在 `ctx.mode === "tui"` 时启用，所有工具和事件逻辑都不依赖 UI。
- 盘口小组件显示实时的 `captured_at`；模型使用的 view 有自己的 `captured_at`，两者不一定相同。

### 12.5 上下文与压缩

- 唤醒消息和摘要都有长度上限，内容紧凑；原始盘口不写进会话。
- 长时间运行会触发 Pi 的上下文压缩。watch 的备注会在唤醒时原样带回，`status` 动作也可以随时重建全貌，所以模型在压缩后仍能接上自己的计划。
- 可选功能（默认关闭）：用 Pi 的 `context` 事件，在单次请求中把超过 N 分钟的旧输出折叠成一行摘要（view_id、时间、要点）。这样能节省 token，代价是 prompt 缓存前缀会失效，需要评估后再开启。

## 13. 资源、故障与 IBKR 消息

### 13.1 资源预算

下列预算都按字节或实测负载设定，可以配置，不按标的数写死：

| 项目 | [初值] | 超限行为 |
|---|---|---|
| reducer 入口队列 | 16 MiB（估算） | 视为已知数据丢失：重建受影响的请求，切断观察段 |
| 详细历史 | 全局 256 MiB，按活跃度分配，每个标的目标 300 秒 | 淘汰最旧的可重放块，更新 `available_from` |
| 采样与价格带积分 | 全局 64 MiB | 缩短回看范围并披露 |
| 冻结 view | 全局 128 MiB（含 pin 住的块） | 淘汰未 pin 的 view；新 view 可以声明缩短历史，或报容量不足 |
| 输出 | read ≤ 16 KiB；details 每页 ≤ 40 KiB | 分页，并保留遗漏计数 |
| IPC 帧 | ≤ 1 MiB | 按协议错误处理 |
| UI | ≤ 4 Hz | 丢弃旧帧，不影响数据 |
| 录制 | 队列 8 MiB；目录上限可配置 | 停止录制并标记缺口 |
| 准入 | reducer 积压 p95 ≤ 100 ms、CPU ≤ 70% | 新订阅返回 `local_capacity_exhausted` |

### 13.2 溢出与故障

四类情况分开处理（采纳 v0.3 的做法）：
- **入口溢出**：属于已知数据丢失。受影响的订单簿不能再当作完整状态，重建请求。
- **历史淘汰**：只缩短回看范围，实时订单簿不受影响。
- **录制溢出**：只停止录制。
- **UI 丢帧**：不影响任何数据。

各输入流的故障互不影响：报价流失败不影响深度订阅，录制失败不影响报价流。

| 码 | 含义[官方] | 处理 |

| 309 | 深度请求数已达上限 | 按 §4.2 回收更低级别并重试一次；仍失败则返回 `depth_capacity_rejected`，列出本包持有的订阅；不推断账户总额 |
| 310 | 取消时找不到对应的深度订阅 | 记录，按幂等处理 |
| 316 | 深度数据被 HALTED，需要重新订阅 | 退避后以新 epoch 重订阅，切断观察段 |
| 317 | 深度数据被 RESET，需先清空再应用新条目 | 清空后重建，epoch + 1；旧 view 仍是有效历史 |
| 101 | TWS 与 API 的行情线合计已满 | 新的报价或观察清单请求失败并报告；不影响已有订阅 |
| 326 | clientId 已被占用 | 报告，提示检查是否还有另一个 Pi 会话 |

### 13.4 请求节奏与重连

- 同一合约 15 秒内最多发起 1 次逐笔请求[官方]。切换层级、重订阅、恢复连接都走同一个节奏检查。
- 可恢复的错误用有限次数的退避重试，并披露下次重试时间。权限和参数错误不重试。`stop` 会使所有待重试的请求失效。
- 重连后产生新的数据段，不把旧窗口说成连续。

**模型评估**
- **主动调用的价值**：沿用 v0.3 的分层输入对照，逐层增加输入：只有 L1 → 加顶档 → 加多档快照 → 加多档变化过程 → 加报价参照 → 加成交流。每一层比较事实误读、反证发现、结论有用性、耗时和 token。

- **计划闭环**：模型能否把论点写成合理的 watch，触发后能否正确更新计划。
- **真值来源**：真值不能来自本包自己未经验证的判定。没有逐订单真值时，评估只核对“观察到了哪些字段和计算”。

## 附录 B. 交易日核对清单

1. `reqMktDepthExchanges` 的原始结果，以及 `serviceDataType` 的取值。
2. SMART、ISLAND、IEX 三种模式：
   - 回调类型；
   - `marketMaker` 的取值；
   - 行排序；
   - 满行后的尾部行为；
   - “行数不足即全侧”是否成立。
3. 深度请求的计数：同一标的同时开 SMART 与直连算几个；TWS 的深度窗口是否占用名额。
4. `numRows` 的实际上限。
5. 各流的数量单位：深度、逐笔、RT Volume、报价，核对时 lots 选项保持关闭。
6. 报价参照的实际数据类型，以及是否为综合报价口径。
7. 逐笔成交的交易所代码，包括场外成交的代码；逐笔名额已满时的消息码。
8. RT Volume 的实际颗粒度，与逐笔对比。
9. 盘前、盘后是否有深度数据。
10. 活跃标的的更新频率、reducer 积压和 CPU 占用。
11. `reqMarketRule` 能否取得，以及 tick 换算是否正确。
12. ICE 期货和债券的深度可用性（需要期货交易权限）。
13. 在常规交易时段复测第三方转述的“深度行数为 0”。
